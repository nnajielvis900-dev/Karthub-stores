## 2. Requirements and Design Approach

**Functional requirements:** (F1) add a product with flexible attributes and initial stock; (F2) place a multi-item order that reserves stock and records payment atomically; (F3) update stock without overselling; (F4) show the delivery timeline for a tracking number; (F5) report revenue, best sellers and low stock.

**Non-functional requirements:** correctness under concurrent buyers (ACID), fast lookups on large order tables, flexibility for varied product specifications, and the ability to scale reads and data volume.

**Design approach (polyglot persistence):** MySQL is the system of record for money and stock, where integrity matters most. MongoDB serves the catalogue and order-history views, where flexible, read-heavy documents fit better. Portfolio 5 then distributes the data.

## 3. Portfolio 1: Conceptual and Logical Design

### 3.1 ER model
See `portfolio-1-database-design/er-diagram.md` (Mermaid, renders on GitHub). Entities: Customer, Address, Category, Product, ProductAttribute, Inventory, Order, OrderItem, Payment, Delivery, DeliveryEvent.

Key relationships: Customer 1:N Address; Customer 1:N Order; Category 1:N Product (and a self-reference for sub-categories); Product 1:N ProductAttribute; Product 1:1 Inventory; **Order M:N Product resolved by OrderItem**; Order 1:N Payment (retries/refunds); Order 1:0..1 Delivery; Delivery 1:N DeliveryEvent.

### 3.2 Relational schema (summary of `schema.sql`)

| Table | Primary key | Foreign keys | Other constraints |
|---|---|---|---|
| customers | customer_id | none | `email` UNIQUE |
| addresses | address_id | customer_id → customers (CASCADE) | NOT NULL location fields |
| categories | category_id | parent_id → categories | `name` UNIQUE |
| products | product_id | category_id → categories | `sku` UNIQUE; CHECK `unit_price >= 0` |
| product_attributes | attribute_id | product_id → products (CASCADE) | UNIQUE (product_id, attr_name) |
| inventory | product_id | product_id → products (CASCADE) | CHECK `quantity_on_hand >= 0` |
| orders | order_id | customer_id, shipping_address_id | ENUM status; CHECK total >= 0 |
| order_items | (order_id, product_id) | order_id (CASCADE), product_id | CHECK quantity > 0 |
| payments | payment_id | order_id → orders | ENUM method/status; `transaction_ref` UNIQUE; CHECK amount > 0 |
| deliveries | delivery_id | order_id → orders | `order_id` UNIQUE (1:1); `tracking_number` UNIQUE |
| delivery_events | event_id | delivery_id → deliveries (CASCADE) | none |

**Integrity mechanisms used:** entity integrity (PKs), referential integrity (FKs with chosen cascade rules), domain integrity (ENUMs, `CHECK` constraints, enforced from MySQL 8.0.16), and business rules (no negative stock, no zero-quantity lines).

### 3.3 Normalisation
Starting from one unnormalised order sheet, `Order(order_id, customer_name, email, address, product_names[], prices[], quantities[], payment_method, courier, tracking_no)`:

1. **1NF:** the repeating group of products becomes `order_items`, one row per product per order, with atomic values.
2. **2NF:** product name, category and price depend only on `product_id`, not the whole `(order_id, product_id)` key, so they move to `products`.
3. **3NF:** customer email/phone depend on `customer_id`, not `order_id` (a transitive dependency), so they live in `customers` and `addresses`; category names move to `categories`.
4. **BCNF check:** every determinant in each table is a candidate key (e.g. `sku`, `email` and `tracking_number` are candidate keys of their tables).

**Deliberate denormalisation (justify in your reflection):** `order_items.unit_price` records the price *at the time of sale* so historical orders don't change when the catalogue price changes; `orders.total_amount` is a derived value kept for fast reads and is set inside the order transaction.

**Design trade-off:** `product_attributes` uses an entity-attribute-value (EAV) layout so a phone (RAM, storage) and a shirt (size, material) share one schema. The cost is weak typing (all values are strings) and slower attribute queries (Q6), which motivates the document model in Portfolio 4.

## 5. Portfolio 3: Transactions and Concurrency

**Business transaction (place order):** lock each stock row in `product_id` order, check stock, insert `orders`, `order_items`, `payments`, decrement `inventory`, COMMIT; on any error ROLLBACK (`karthub_ops.place_order` and `sp_place_order`).

| Evidence | Script | What it shows |
|---|---|---|
| COMMIT | `transactions_demo.py` §1, §3 | Two-item order commits; stock decremented |
| ROLLBACK | §2, §3 | Out-of-stock item aborts the whole order; order count and stock unchanged |
| SAVEPOINT | §4 | Partial rollback (invalid item) while keeping the order |
| Isolation | §5 | READ COMMITTED shows a non-repeatable read; REPEATABLE READ (InnoDB default) keeps a stable snapshot |
| Lost update | `concurrency_demo.py` A | Two buyers of the last unit both succeed (overselling) when using read-then-write |
| Fix 1 | B | `SELECT ... FOR UPDATE` serialises buyers; second sees 0 and is refused |
| Fix 2 | C | Atomic `UPDATE ... WHERE quantity_on_hand >= 1` and checking the affected row count |
| Deadlock | D | Opposite lock order makes InnoDB abort one transaction (error 1213); consistent lock order removes it |

Save the console output to `evidence/` and take screenshots. In the write-up explain **why** the unsafe version fails: under REPEATABLE READ, plain `SELECT` is a snapshot read, so both sessions compute the same new value.

## 6. Portfolio 4: NoSQL and Advanced Data Models (MongoDB)

**Model choice:** document store. Three collections (`products`, `customers`, `orders`) loaded from `portfolio-4-nosql/data/*.json`.

| Collection | Embedding decision | Reason |
|---|---|---|
| products | attributes as a nested object; stock embedded | Different products have different attributes; one read returns everything |
| customers | addresses embedded | Small, bounded, always read with the customer |
| orders | items, payment, shipping address, delivery and tracking events embedded; customer **snapshot** (id, name, email) | An order is read as a whole; history must not change if the customer edits their profile |

**References vs embedding:** order items keep `productId` (reference) plus a copy of name and price (snapshot); category revenue uses `$lookup` back to `products`.

**Indexes (`load_mongo.py`):** unique `sku`, `orderNo`, `email`; compound `{customer.id, createdAt:-1}` for order history; sparse unique `delivery.trackingNo` (unpaid orders have no delivery); `{category.id, price}` and `attributes.colour` for catalogue filters.

**Operations (`mongo_queries.py`):** add product (schema-free attributes), attribute search, guarded stock update, **multi-document ACID transaction** for place-order (requires the replica set), delivery tracking with `$push` of a new event, aggregations (revenue per category, top customers, low stock), and `explain()` for index evidence.

**Suitability:** *Good fit:* flexible catalogue attributes, single-read order/tracking retrieval, horizontal scaling. *Poor fit:* heavy cross-entity joins and strict financial integrity, so payments and stock remain authoritative in MySQL. Optional extras to mention: Redis (key-value) for carts/sessions, a graph database for "customers also bought".

| Aspect | MySQL | MongoDB |
|---|---|---|
| Schema | Fixed, enforced | Flexible, validated by application (or JSON Schema) |
| Product attributes | EAV rows, string values | Native nested, typed values |
| Order retrieval | 4-table join | Single document |
| Consistency | Strong ACID, mature locking | Strong within a document; multi-document transactions available with cost |

## 7. Portfolio 5: Distributed and Cloud Database Exercise

### 7.1 Practical setup
`docker-compose.yml` starts MySQL and a **3-node MongoDB replica set**. `replica_set_demo.py` provides: `--init` (elections; `mongo1` priority 2), `--status` (PRIMARY/SECONDARY/DOWN), `--replication` (write with `w=majority`, read back from each node), `--writeconcern` (latency of `w=1` vs `w=majority`). **Failover test:** `docker stop karthub-mongo1`, run `--status` again and screenshot the newly elected primary.

### 7.2 Design discussion

| Topic | KartHub design |
|---|---|
| **Replication** | MySQL: one source for writes plus read replicas for browsing and reports (`mysql-replication-notes.md`). MongoDB: replica set for automatic failover. Async replicas lag, so read-your-own-writes traffic (order confirmation) goes to the primary. |
| **Sharding / partitioning** | Orders sharded by **hashed `customer_id`**: even distribution, and a customer's history stays on one shard. Avoid sharding by `order_date` (hot shard on newest data). Products are read-heavy and small: replicate/cache instead. `mysql_partition_demo.sql` shows HASH partitioning and partition pruning; note MySQL partitioned tables cannot use foreign keys. |
| **Consistency (CAP/PACELC)** | Payments and stock: consistency first (CP): `w=majority`, primary reads. Catalogue and tracking views: availability and low latency first (AP-style), accepting stale reads. |
| **Availability** | Multi-node/AZ deployment, automatic election (demonstrated), backups with point-in-time recovery, defined RPO/RTO. |
| **Cloud deployment** | Managed MySQL (e.g. Amazon RDS/Aurora, Google Cloud SQL, Azure Database for MySQL) and MongoDB Atlas: managed backups, failover, scaling, encryption at rest/in transit, private networking, IAM. Discuss cost versus operational effort. |

## 9. Limitations and Possible Improvements
Single-currency pricing; one address per customer in the sample data; simplified payment states (no gateway integration); no audit table or stock-movement ledger; hash partitioning demo has no foreign keys; MongoDB order snapshots can drift from the customer's current profile by design. Future work: stock reservations with expiry, a ledger table, full-text product search, and read/write splitting in the application layer.
